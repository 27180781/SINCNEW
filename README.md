# מערכת אפיון אישיות לפי ארבעת יסודות הבריאה 🔥💧🌬️🌱

מערכת שמשקללת תשובות של משתתפים במבחן אישיות, מחשבת את הרכב **ארבעת היסודות**
(אש · מים · רוח · עפר) של כל אחד באחוזים, ומצמידה לו את **סוג האישיות הקרוב ביותר**
מתוך מאגר של מאות סוגים — לפי המרחק המינימלי בין פרופיל היסודות שלו לבין הסוגים.

המערכת כוללת **מבחן ציבורי** ו**פאנל ניהול** מלא.

---

## הפעלה

נדרש Node.js 20 ומעלה.

```bash
node server.js          # מצב JSON — ללא npm install כלל
# או:  npm start
```

* מבחן:   http://localhost:3000/
* ניהול:  http://localhost:3000/admin

### שכבת אחסון גמישה
המערכת בוחרת אחסון לפי משתנה הסביבה `DATABASE_URL`:

| מצב | תנאי | אחסון |
|-----|------|-------|
| **פיתוח** | אין `DATABASE_URL` | קובץ `data/db.json` (ללא תלויות, ללא התקנה) |
| **פרודקשן** | `DATABASE_URL` מוגדר | PostgreSQL (סכימה + זריעה נוצרות אוטומטית בהפעלה ראשונה) |

```bash
# הרצה מול Postgres מקומי:
npm install                                   # נדרש רק במצב Postgres (בשביל החבילה pg)
DATABASE_URL=postgres://user:pass@localhost:5432/elements node server.js
```

שכבת האחסון מופשטת ב-`src/repo/` — שני מימושים (`JsonRepo` / `PgRepo`) עם ממשק זהה,
מכוסים בבדיקת פאריטי משותפת (`test/repo.test.js`).

### הגנת הפאנל (אופציונלי)
כברירת מחדל ה-API פתוח (נוח לפיתוח מקומי). כדי להגן על נתיבי הניהול, הריצו עם טוקן:

```bash
ADMIN_TOKEN=סוד-כלשהו node server.js
```

אז כל נתיב שאינו ציבורי (הציבוריים: `GET /api/config`, `POST /api/score`, `GET /api/health`)
ידרוש כותרת `x-admin-token`. פאנל הניהול יבקש את הטוקן אוטומטית וישמור אותו בדפדפן.

```bash
npm test      # הרצת בדיקות מנוע השקלול
npm run reset # איפוס הנתונים לברירת מחדל
```

## פריסה ל-CapRover (שתי אפליקציות: DB + Web)

### שלב 1 — אפליקציית ה-PostgreSQL
1. ב-CapRover: **Apps → One-Click Apps/Databases → PostgreSQL**.
2. שם אפליקציה: למשל `elements-db`; גרסה `16`; הגדירו סיסמה חזקה.
   (התבנית כוללת נפח פרסיסטנטי אוטומטי — הנתונים נשמרים.)
3. הכתובת הפנימית של ה-DB בתוך CapRover: `srv-captain--elements-db` (פורט 5432).

### שלב 2 — אפליקציית ה-Web
1. **Apps → Create New App** (למשל `elements`).
2. **Deployment**:
   * מ-GitHub: כתובת הריפו + הענף `claude/personality-elements-system-ww1x3s`.
   * או מהמחשב: `npm i -g caprover` ואז `caprover deploy`.
3. **Environmental Variables**:
   ```
   DATABASE_URL=postgres://postgres:הסיסמה@srv-captain--elements-db:5432/postgres
   ADMIN_TOKEN=בחרו-סוד-חזק
   GAME_TOKEN=סוד-לאינטגרציית-המשחק
   YEMOT_TOKEN=077000000:הסיסמה   # לצינתוק דרך ימות המשיח (אופציונלי)
   ```
   * `DATABASE_URL` — מחבר את ה-Web ל-DB (הסכימה והזריעה נוצרות אוטומטית בהפעלה ראשונה).
   * `ADMIN_TOKEN` — **חשוב!** בלעדיו פאנל הניהול חשוף לכל.
   * `GAME_TOKEN` — אופציונלי; אם מוגדר, כתובת ה-webhook בעורך המשחק חייבת לכלול `?token=...`.
   * `YEMOT_TOKEN` — אופציונלי; טוקן ימות המשיח (בפורמט `מספר:סיסמה`) לשליחת צינתוק בסיום קליטת תוצאות.
4. **HTTP Settings** — הפעילו Enable HTTPS + Force HTTPS.

הקונטיינר מאזין על פורט 80 (ברירת המחדל של CapRover) — אין צורך בהגדרת פורט ידנית.

> במצב Postgres אין צורך בנפח פרסיסטנטי על אפליקציית ה-Web — כל הנתונים ב-DB.
> (אם תריצו בלי `DATABASE_URL`, האחסון הוא `data/db.json` וצריך נפח פרסיסטנטי ל-`/app/data`.)

## איך זה עובד

### 1. שאלות ומיפוי יסודות
לכל שאלה יש 4 אפשרויות, וכל אפשרות ממופה ל**יסוד** (`fire`/`water`/`air`/`earth`).
המיפוי נשמר לכל שאלה בנפרד — כך שסדר היסודות יכול להשתנות בין שאלה לשאלה.
זהו "השיוך של כל שאלה לערך".

### 2. שקלול
לכל משתתף המערכת סופרת כמה תשובות נפלו בכל יסוד, וממירה לאחוזים
(שסכומם 100). היסוד עם האחוז הגבוה ביותר הוא ה"דומיננטי".

### 3. מאגר סוגי האישיות
כל סוג אישיות מוגדר ע"י פרופיל אחוזים, למשל `{ fire: 40, water: 30, air: 20, earth: 10 }`.
המערכת מגיעה עם **286 סוגים** שנוצרים אוטומטית (כל צירוף אחוזים בצעד של 10%),
וניתן להוסיף/לערוך/לייבא/לחדש דרך פאנל הניהול.

### 4. התאמה
עבור כל משתתף מחושב המרחק (אוקלידי כברירת מחדל) בין פרופיל היסודות שלו לכל
סוג אישיות. הסוג עם **המרחק הקטן ביותר** הוא ההתאמה. מוצג גם אחוז דמיון
(`100% = התאמה מושלמת`) וכן ההתאמות הקרובות הבאות.

## מבנה קלט המשתתפים (ה-JSON שהמערכת מקבלת)

```json
{
  "name": "כיתה א' 2026",
  "participants": [
    { "id": "p1", "name": "דנה", "answers": { "q1": "A", "q2": "C", "q3": "fire" } },
    { "id": "p2", "name": "יוסי", "answers": ["B", "B", "D"] }
  ]
}
```

ערך התשובה סלחני ומזוהה אוטומטית לפי:
* **אות** — `A`/`B`/`C`/`D` (לפי מיקום האפשרות)
* **מספר** — `1`–`4` (אינדקס), או `0`-מבוסס
* **מזהה אפשרות** — למשל `q1o3`
* **מפתח יסוד** — `fire`/`water`/`air`/`earth`

`answers` יכול להיות אובייקט (`{ "q1": ... }`) או מערך לפי סדר השאלות.
מפתחות מספריים באובייקט הם **1-מבוססים** (`"1"` = השאלה הראשונה); מערך הוא 0-מבוסס לפי מיקום.

## אינטגרציית משחק (webhook)

מערכת המשחק ("משחק פונקציה") שולחת את תוצאות המשחק בסיום, מדפדפן המנחה, ל-endpoint:

```
POST /api/games/webhook          Content-Type: application/json   (גוף = מטען המשחק)
GET  /api/games/webhook?payload=<JSON מקודד ב-URL-encoding>       (חלופה, מוגבל באורך)
```

* **CORS + preflight** — הבקשה מגיעה cross-origin מהדפדפן. השרת עונה ל-`OPTIONS` (204)
  ומחזיר `Access-Control-Allow-Origin/Methods/Headers`, כך שה-POST האמיתי נשלח.
* **טוקן אופציונלי** — הגדירו `GAME_TOKEN=סוד` בשרת, והוסיפו `?token=סוד` לכתובת בעורך המשחק.
* **מניעת כפילויות** — לפי `gameId + sentAt` (אם המנחה נכנס שוב לשקופית, לא נוצר מפגש כפול).
* **תגובה מהירה 2xx** — מחזיר `200` עם `{ ok, stored|duplicate, batchId, participants }`.

### מה קורה עם התוצאות
כל משתתף מהמשחק (`number`, `name`, ורשימת `answers` של `{queId, answerId}`) מומר
למשתתף במערכת שלנו, מחושב לו **פרופיל יסודות** ומוצמד **סוג אישיות** — התוצאה נשמרת
כ**מפגש** (עם תג 🎮) שזורם ללוח הבקרה, לסטטיסטיקות ולצפייה, יחד עם ניקוד המשחק המקורי.

### צינתוק אוטומטי (ימות המשיח)
בסיום קליטת תוצאות, אם מופעל בהגדרות ומוגדר `YEMOT_TOKEN`, המערכת שולחת **צינתוק**
(דרך `RunTzintuk` של call2all) לכל המשתתפים שיש להם תוצאה מוכנה. השליחה מתבצעת
ברקע (fire-and-forget) כדי לא לעכב את התשובה למשחק, וסטטוס השליחה מוצג בטאב "קלט Webhook".
מפעילים ומגדירים (callerId, משך צינתוק, למי לשלוח) בטאב **הגדרות → צינתוק**, שם גם כפתור בדיקה.

### טקסט פתיח אישי לשיחה נכנסת (ימות המשיח)
כשהמתקשר חוזר לימות אחרי הצינתוק, שלוחת API (`type=api`, `api_url_post=yes`) קוראת ל-`/api/get-intro-text`
עם `ApiPhone`. השרת מנתח גם POST בפורמט form-urlencoded (כפי שימות שולחת) ומחזיר את הטקסט.
פורמט התשובה (ניתן לבחור ב-`?format=`):
* **ברירת מחדל** — `id_list_message` (משמיע וממשיך, מתאים ל-`api_end_goto`)
* `?format=read` — `read=t-<שורה1>.t-<שורה2>...`
* `?format=text` — טקסט גולמי לתצוגה בדפדפן

הטקסט לפי התוצאה האחרונה של אותו מספר:

```
שלום ל<שם>            (אם אין שם: "שלום לך")
על פי הנתונים שהגיעו מהמשחק התוצאה האישית שלך היא כדלהלן
היסוד הדומיננטי שלך הוא יסוד ה<X>     (רק אם יש דומיננטי יחיד; בתיקו — מדולג)
ובפירוט
<אחוז> אחוז יסוד ה<...>   (לכל יסוד, מהגבוה לנמוך)
מיד תועבר לשמוע בפירוט על התכונות שמאפיינות אותך
```

הדומיננטי נקבע לפי היסוד עם הכי הרבה תשובות; אם כמה יסודות שווים במקסימום — שורת הדומיננטי מדולגת.
אם המספר לא נמצא / לא ענה — מוחזר טקסט מתאים. הכתובת מוצגת בפאנל (טאב "שיוך משתתפים").

**סימולטור שיחה** (בטאב "שיוך משתתפים"): מזינים שם + אחוזי יסודות (או טוענים תוצאה קיימת לפי טלפון),
רואים את הטקסט, ו**מאזינים** בהקראת דפדפן. לבדיקת שיחה אמיתית — כפתור "שמור דמו למספר" יוצר תוצאה
עבור מספר טלפון, וכשמתקשרים לימות (עם שלוחת API שמצביעה על `get-intro-text`) שומעים בדיוק אותה.

### מיפוי שאלות/תשובות
כדי שהתשובות יתמפו נכון ליסודות, בטאב **שאלות** מגדירים לכל שאלה:
* `queId` — מזהה השאלה במערכת המשחק.
* `answerId` — לכל אפשרות, מזהה התשובה במשחק, בצירוף היסוד שהיא מייצגת.

אם לא מוגדרים — נעשה מיפוי **לפי מיקום** (queId ה-N ← השאלה ה-N, answerId ה-M ← האפשרות ה-M).
כתובת ה-webhook המלאה מוצגת בטאב "שיוך משתתפים" בפאנל הניהול (עם כפתור העתקה).

### ייבוא מיפוי מ-Excel/CSV
בטאב **מיפוי יסודות** אפשר להעלות קובץ שממפה את כל השאלות בבת אחת. מבנה הקובץ:

| מספר שאלה | תשובה 1 | תשובה 2 | תשובה 3 | תשובה 4 |
|-----------|---------|---------|---------|---------|
| 7 | water | fire | earth | air |
| 8 | fire | earth | air | water |

* עמודה ראשונה = `queId`; שאר העמודות = היסוד שכל `answerId` מייצג.
* ערכי יסוד: `fire/water/air/earth` או `אש/מים/רוח/עפר`.
* `POST /api/questions/import-mapping` עם `{ dataBase64 }` (xlsx/csv) או `{ csv }` / `{ rows }`,
  ו-`mode`: `replace` (החלפה מלאה) או `merge` (עדכון לפי queId, שמירת השאר).
* לצד הייבוא יש **עורך-רשת** לעריכה ידנית שאלה-שאלה (בדיוק כמו הטבלה).
